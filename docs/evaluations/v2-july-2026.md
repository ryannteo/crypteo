# V2 evaluation run: July 2026 windows

## Summary

Crypteo ran its first planned evaluation under
[ADR-013](../decisions/ADR-013-v2-evaluation-scope.md): 22 single-candidate windows
from July 2026, after the research model's training cutoff, each replayed once
with the scanner-only baseline and once with fresh Claude research. Claude declined
every candidate (19 `NO_TRADE`, 3 `ABSTAIN`, 0 `TRADE`). The baseline traded 20 of
them and lost 409.33 USD net. A separate process with no API key reproduced every
research decision and every metric from the stored artifacts.

Because research never chose `TRADE`, this run shows that research acted as a
blanket veto in this period, not that it can tell good setups from bad ones; a
constant "never trade" rule produces the same numbers. The stored reasoning shows
why: the available evidence gave research no route to a well-supported `TRADE`
(see [Why research declined](#why-research-declined)). The run is a demonstration
of the evaluation harness, as ADR-013 planned, not a performance result.

Reaching a completed run took four aborted attempts and three fixes to the
research workflow. Each failure was diagnosed from the stored research journal;
they are recorded below.

## How the windows were chosen

`plan_windows` with purpose `EVALUATION`, `planning_start` 2026-07-01T00:00:00Z and
limit 22. The planner scanned each pair once and walked the lower-band crossings in
time order (BTC, ETH, SOL for ties), using scanner signals only, never prices or
outcomes. Each selected window starts at its signal and lasts 6 hours, the
maximum holding period, so every baseline trade resolves inside it.

26 candidates were considered from 2026-07-05 to 2026-07-17; 22 were selected and
4 were excluded as `OVERLAPPING_CANDIDATE` (another crossing of the same pair
inside the window). Plan ID
`sha256:25e44d943bee47171dd729b94b358d8791a780426302929bccc5994a5edbe73a`.

July 2026 is after the model's June 2026 training cutoff, and the V1 release
inspected only data from 2026-09-01 onward, so no part of this period had been
inspected before. No window decisions or baseline outcomes from the aborted runs
were viewed before the completed run.

## Interpretation

- Research declined all 22 candidates with self-assessed confidence between 52
  and 62. With no `TRADE` decisions, the `taken` group is empty, so this run
  cannot measure whether research selects better trades than the baseline.
- In this 12-day stretch, lower-band crossings mostly did not revert within six
  hours: 15 of 20 baseline trades lost, most at the time limit. Avoiding them
  saved 409.33 USD, but any rule that never trades would have done the same.
- The three largest declined winners (+54.52, +43.68, +36.23) were one market
  move, all three pairs crossing at 2026-07-06 13:00.
- Signals cluster in time across correlated pairs; the 22 windows cover about a
  dozen distinct market moves.

## Why research declined

The stored assessments and critiques give the same reasons in nearly every
window, which points to the evidence available rather than a judgment about July:

| Reason cited by the assessment or critic | Windows |
|---|---|
| Relative strength vs the other pairs unavailable (single-pair windows) | 22 of 22 |
| No historical base rate for the trigger's reversion | about 16 |
| The only supporting evidence is the trigger itself | about 14 |
| No higher-timeframe (4h/daily) context | about 14 |
| No post-trigger confirmation (unavailable by design at decision time) | about 11 |
| No trigger-bar candle structure (wicks, close location) | about 8 |

At a lower-band crossing, trend and momentum read bearish by construction. The
tools that could support a reversion case either do not exist or were unavailable
in single-pair windows, so the research workflow had no route to a well-supported
`TRADE`. The run therefore measured the research setup's evidence coverage, not
selection skill. Two assessments also flagged ambiguous `levels` semantics
(whether the window includes the trigger bar, and whether lows are close-based or
intrabar), which the tool descriptions should state.

## Reaching a completed run

Every completed research run used all 8 tool attempts, so the final forced
investigation turn, and the synthesis that follows it, are the normal path, not an
edge case. That is where four attempts stopped. Each stop was an operational
failure that aborted the run, as specified; none became a `NO_TRADE` or a skipped
window.

| Trial | Code | Outcome | Cause, from the stored journal |
|---|---|---|---|
| `v2-evaluation-1` | `f544e4e` | Stopped at window 003 (ETH-USD, 2026-07-06 13:00) | Investigation call 9 returned `{"summary":"","relevant_evidence_ids":[],"remaining_gaps":[]}`; a blank summary fails validation |
| `v2-evaluation-2` | `6d87986` | Stopped at window 001 (SOL-USD, 2026-07-05 02:00) | API key not set in the shell; one attempt was reserved, no API call was made |
| `v2-evaluation-3` | `6d87986` | Stopped at window 001 (SOL-USD, 2026-07-05 02:00) | Same empty completion on call 9, despite the prompt fix |
| `v2-evaluation-4` | `e8342e5` | Stopped at window 003 (ETH-USD, 2026-07-06 13:00) | Call 9 succeeded; `draft_thesis` returned every field blank (309 output tokens, `end_turn`) |

Fixes, in order:

1. `6d87986`: the investigation prompt requires a nonblank summary, including
   on the final turn. It did not stop the failure.
2. `e8342e5`: the final investigation call offers no tools, since none may be
   used; the journal rebuilds requests with the same rule. The investigation
   turn then succeeded, but the empty output moved to the next stage.
3. `f76072b`: when a stage's structured output fails validation, the workflow
   asks that stage once more, telling it which fields failed (at most 2 re-asks
   per run, all journaled and rebuilt on load). The runtime still never fills in
   content, and a failed re-ask still ends the run.

Claude structured outputs cannot enforce a minimum string length, so blank
strings are schema-valid on the wire; project validation rejects them. Before
fix 3, about 3 of 10 real research runs ended this way. In the completed run, 1
of 22 windows needed a re-ask (window 002, BTC-USD at 2026-07-06 13:00,
investigation stage), and it succeeded.

A one-window `PLUMBING` rehearsal on contaminated June data (BTC-USD at
2026-06-09 01:00, commit `f544e4e`) verified the API path and key-free
reproduction before the evaluation; it is not part of the results.

## Limitations

- 22 windows, about a dozen independent market moves, in one 12-day period.
  Descriptive only; no statistical claim.
- Research never chose `TRADE`, so selection quality is unmeasured; the evidence
  set, not the period, appears to explain this (see "Why research declined").
- Single-pair windows bind one dataset, so relative-strength evidence was
  unavailable to research in every window.
- `OVERLAPPING_CANDIDATE` excluded 4 of 26 candidates; this may bias the sample
  toward candidates whose decline did not continue.
- July 2026 is after the model's training cutoff, but parametric knowledge
  cannot be proven point-in-time pure.
- Fees and slippage are simulation assumptions. Licensed raw Coinbase data is not
  redistributed; reproduction needs the same code, Python and Pydantic versions,
  datasets and research store.
- The run script is kept outside the repository, as in V1.
